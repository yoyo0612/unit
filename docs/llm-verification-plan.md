# LLM 稼働 PC での検証計画

対象: ローカル LLM（Qwen3.6-35B-A3B、llama-server）を動かす自宅 PC
前提: Ryzen 9 5950X / RTX 3070 Ti（VRAM 8GB）/ RAM 96GB / Windows 11 Home
設定の根拠: [llm-model-selection-and-tuning.md](llm-model-selection-and-tuning.md)

この文書は、発表資料で述べた計測値と動作を **この PC で再確認するための計画** です。
実行結果は本文ではなく「記録表」に書き込みます。

---

## 1. 検証の目的

| 目的 | 確認すること |
|---|---|
| 再現性 | 既存の計測値（生成 23 tok/s 前後、VRAM 6.65GB 前後）が再現するか |
| 安定性 | 長時間・長文・複数回の利用で、VRAM 溢れや異常終了が起きないか |
| 機能 | API、tool calling、Minecraft ボットの行動制御が意図どおり動くか |
| 制限の確認 | 発表で「未検証」とした点（別モデル、Thinking 出力など）の状態を把握する |

---

## 2. 事前準備

- 作業は LLM サーバーを停止した状態から始める（`scripts\stop-llm.bat`）。
- 計測中は他の GPU アプリ（ブラウザの動画再生、ゲームなど）を閉じる。ただし「併用時」の検証は別項目で行う。
- 計測の前に、ドライバとビルドを記録する（ドライバが変わると結果も変わるため）。

---

## 3. 検証項目

### 3-1. 環境の確認（各項目とも合否を記録）

| # | 確認内容 | 方法 | 合格条件 |
|---|---|---|---|
| E-1 | GPU とドライバ | `nvidia-smi` | GPU 名が RTX 3070 Ti、VRAM 8GB、ドライバ 610.47 系 |
| E-2 | llama.cpp のバージョン | `C:\llm\bin\llama-server.exe --version` | b11675 |
| E-3 | RAM 容量 | `Get-CimInstance Win32_PhysicalMemory \| Measure-Object Capacity -Sum` | 合計 96GB |
| E-4 | モデルファイル | ファイルサイズを確認 | `Qwen3.6-35B-A3B-UD-Q4_K_M.gguf` が約 20.6GB |

### 3-2. 起動と API

| # | 確認内容 | 方法 | 合格条件 |
|---|---|---|---|
| A-1 | 既定設定での起動 | `scripts\start-llm-server.ps1`（引数なし） | エラーなく起動し、準備完了の表示が出る |
| A-2 | モデル一覧 | `curl http://127.0.0.1:8080/v1/models` | モデルが 1 件返る |
| A-3 | 応答 | `chat/completions` に短い質問を送る | 応答が返る。エラーなし |
| A-4 | 待ち受けアドレス | `Get-NetTCPConnection -LocalPort 8080` | LocalAddress が `127.0.0.1` のみ |
| A-5 | 起動から初回応答まで | 起動直後に A-3 を実行し、時間を記録 | 時間を記録（参考値） |

### 3-3. 性能（既定構成）

既定値: `-NCpuMoe 40`、`-Ctx 131072`、`-KvType q8_0`、`-Threads 12`、`-UBatch 2048`

| # | 確認内容 | 方法 | 合格条件 |
|---|---|---|---|
| P-1 | 生成速度の再現 | 同じプロンプトで 3 回実行し、tg（tok/s）を記録 | 3 回の平均が 23.0 tok/s の ±10%（20.7〜25.3）に入る |
| P-2 | プロンプト処理 | 約 4,800 トークンの入力で 3 回計測 | 記録（前回 566 tok/s が目安） |
| P-3 | VRAM 使用量 | 計測中に `nvidia-smi` を 1 秒間隔で記録 | ピークが 7.5GB 未満（溢れないこと） |
| P-4 | 計測の再現性 | P-1〜P-3 の結果を並べ、ばらつきを確認 | 3 回のばらつきを記録（傾向の確認が目的） |

### 3-4. 配置の比較

| # | 確認内容 | 方法 | 合格条件 |
|---|---|---|---|
| C-1 | `-NCpuMoe 33` の速度 | `-NCpuMoe 33 -Ctx 16384 -KvType f16` で P-1 と同様に 3 回 | 記録（前回 27.6 tok/s、VRAM 7.28GB） |
| C-2 | `-NCpuMoe 29` の VRAM 溢れ | `-NCpuMoe 29` で起動し、生成速度と VRAM を記録 | 速度低下が再現するか（前回は約 19 tok/s） |
| C-3 | 併用時の余裕 | `-NCpuMoe 34` で起動し、動画再生などと同時に VRAM を記録 | 併用中も溢れないこと |

> C-2 は速度が落ちるだけで、VRAM が溢れた状態のまま長時間動かすのは避ける。確認後は必ず既定値に戻す。

### 3-5. 文脈長

| # | 確認内容 | 方法 | 合格条件 |
|---|---|---|---|
| L-1 | 128K（既定） | 約 10 万トークンの文書に 2 つの合言葉を埋め込み、両方を答えさせる | 両方正答 |
| L-2 | 262K | `-Ctx 262144` で起動し、約 20 万トークンの文書で同じ確認 | 両方正答。VRAM を記録（前回 7.54GB） |
| L-3 | 文書の作り方 | 合言葉の位置（前半・後半）と文書の内容を記録 | 次回も同じ条件で比べられること |

- 長文の文書は、検証ごとに新しく生成する（同じ文書の使い回しで答えを覚えさせないため）。

### 3-6. tool calling（Minecraft ボット）

前提: Minecraft サーバー（`scripts\start-minecraft-server.ps1`）と LLM サーバーを起動しておく。

| # | 確認内容 | 方法 | 合格条件 |
|---|---|---|---|
| T-1 | 接続 | `scripts\start-minecraft-bot.ps1` を実行し、Minecraft から見えるか確認 | ボットがスポーンする |
| T-2 | 返事のみの指示 | 「こんにちは」など、行動が不要な発言を 3 種類送る | 余計なツールを使わず、`say` で返事する |
| T-3 | 行動の指示 | 「ジャンプして」「前に歩いて」など、行動を伴う指示を 5 種類送る | 指示に合ったツールを呼び、行動が起きる |
| T-4 | 停止 | 歩行中に「止まって」と送る | `stop` が呼ばれ、移動が止まる |
| T-5 | 複合の指示 | 「後ろに 2 秒歩いてから手前のブロックを掘って」 | 2 つのツールを順に使い、結果を `say` で伝える |
| T-6 | 曖昧な指示 | 「いい感じにして」 | 実行可能な行動に落とし込むか、質問を返すこと（どちらでもよいが記録する） |
| T-7 | 引数の範囲外 | 「30 秒歩いて」 | `bot.js` の上限（5 秒）に丸められること |
| T-8 | 思考出力 | 応答 JSON の `reasoning_content` の有無を確認 | `enable_thinking: false` で出力が空または無いこと |

記録項目（T-2〜T-6）: 発言内容、呼ばれたツール、ラウンド数、行動が起きたか、応答までの秒数。

### 3-7. 好奇心駆動型学習の環境

| # | 確認内容 | 方法 | 合格条件 |
|---|---|---|---|
| R-1 | venv と PyTorch | `.venv` を有効化し、`python -c "import torch; print(torch.cuda.is_available())"` | `True` |
| R-2 | 動作確認スクリプト | `python scripts\check_env.py` | GPU 名、VRAM 8.0GB、MiniGrid の 10 ステップ実行が表示される |

> LLM サーバーと同時に実行すると VRAM を取り合う。R-1、R-2 は LLM サーバーを停止した状態で行う。

## 5. 判定の方針

- **数値**: 合格条件は前回計測値を基準にした目安。外れた場合は原因を切り分けてから判断する（ドライバ更新、他アプリの常駐、バッテリーや電源設定などを確認）。
- **機能**: tool calling は、意図どおりに行動した割合で評価する（例: T-3 で 5 回中何回成功したか）。
- **失敗の扱い**: 失敗は隠さず記録する。発表では「未検証」「条件付きで成立」などの言い方に揃える。

## 6. 検証後にまとめること

1. 記録表の結果を、発表資料の表 5、表 6、表 11（進捗）と照合する。
2. 数値が前回と大きく異なる場合、発表資料の数値を書き換えるか、「条件付きの結果」として注記する。
3. tool calling の結果は、Minecraft ボットの設計（`bot.js`）を改善する材料にする。
4. 検証で見つかった問題は、GitHub の Issue か、この文書の末尾に追記する。
