# ローカル LLM のモデル選定と最適化の記録

対象: RTX 3070 Ti（VRAM 8GB）/ RAM 96GB / Ryzen 9 5950X（16 コア / 32 スレッド）/ Windows 11 Home

この文書は、ローカル LLM の環境を作る過程で行った **モデル選定の理由** と **最適化の判断・計測結果** をまとめたものです。
導入手順そのものは [local-llm-setup.md](local-llm-setup.md) を参照してください。

> 注意: 数値は、この PC での計測（約 4,800 トークンのプロンプト + 256 トークン生成、または長文の確認）に基づきます。
> 他の個体・ドライバ・llama.cpp のビルドでは変わる可能性があります。

---

## 1. 結論（現在の構成）

| 項目 | 採用 |
|---|---|
| モデル | `unsloth/Qwen3.6-35B-A3B-GGUF`（`Qwen3.6-35B-A3B-UD-Q4_K_M.gguf`、約 20.6GB） |
| 推論エンジン | llama.cpp b11675（CUDA 12.4 版）の `llama-server` |
| 既定の起動構成 | MoE expert を全 40 層 CPU / RAM に置く（`--n-cpu-moe 40`）、KV キャッシュ q8_0、コンテキスト 128K |
| 実測（既定） | 生成 約 23 tok/s、プロンプト処理 約 566 tok/s（短いプロンプト時）、VRAM 約 5.4〜6.7GB |
| 起動方法 | `scripts\launch-llm.bat`（ダブルクリック）または `scripts\start-llm-server.ps1` |
| API | `http://127.0.0.1:8080/v1`（OpenAI 互換、API キー不要） |

## 2. モデル選定

### 2-1. 制約

- VRAM は 8GB しかなく、モデル全体（約 20GB 以上）は載らない
- システム RAM は 96GB あり、モデルを丸ごと置くには十分
- したがって「GPU にできるだけ多く載せ、残りを RAM で受ける」前提で選ぶ必要がある

### 2-2. Qwen3.6-35B-A3B を選んだ理由

- **MoE（Mixture of Experts）構造**: 総パラメータは 35B だが、1 トークンで使うのは約 3B 相当（名前の A3B は active 3B を指す）。
  そのため、expert を CPU 側に置いても生成速度が実用域に残る
- **Q4_K_M で約 20.6GB**: RAM 96GB に余裕を持って収まる。手元の計測でも、RAM 側に寄せた状態で 20 tok/s 台を出せた
- **コンテキストの上限が大きい**: 学習時コンテキストは 262,144。128K〜262K の長文を扱える（後述の確認で動作を確かめた）
- **配布元**: Unsloth の GGUF（UD 量子化）を使用

### 2-3. 量子化の選び方

| 量子化 | 容量 | 判断 |
|---|---|---|
| Q4_K_M | 約 20.6GB | **採用**。品質と容量のバランスが良い基本形 |
| Q3 / IQ3 系 | より小さい | 品質低下が大きいため、VRAM に収めることが目的ではないこの構成では見送り |
| Q5 / Q6 系 | より大きい | RAM 余裕はあるが、生成速度（メモリ帯域）を落とすため見送り |

> この PC では「VRAM に収める」ことではなく「RAM と VRAM を組み合わせて動かす」ことが前提なので、量子化は品質寄りの Q4_K_M で十分と判断しました。
> Q5 以上や別モデル（密モデルなど）との比較は、この記録では行っていません。

### 2-4. 推論エンジンの選び方

| 候補 | 判断 |
|---|---|
| llama-server（llama.cpp） | **採用**。`--n-cpu-moe` や `-ctk` など、MoE と KV キャッシュの細かい調整が必要なため |
| Ollama | 導入手順のみ記載。フラグを細かく調整しにくいため、今回の最適化には不向き |
| LM Studio | 導入手順のみ記載。GUI 向けで、起動フラグの管理がしにくいため見送り |

## 3. 最適化の経過

### 3-1. 当初設定と問題

最初は `--n-cpu-moe 30`、`-ub 512`、`-c 16384` で起動していました。
このとき VRAM が 7.94GB まで膨らみ、溢れた分が共有メモリに退避して遅くなっていました。

| 指標 | 当初 |
|---|---|
| pp（プロンプト処理） | 140 tok/s |
| tg（生成） | 21.9 tok/s |
| VRAM | 7.94GB（溢れて遅い） |

### 3-2. 速度優先の調整（`-ncmoe` と `-ub`）

`-ncmoe` と `-ub`（物理バッチサイズ）の組み合わせを実サーバーで計測しました。

| `-ncmoe` | `-ub` | pp (tok/s) | tg (tok/s) | VRAM |
|---|---|---|---|---|
| 30 | 512 | 140 | 21.9 | 7.94GB |
| 32 | 512 | 358 | 28.4 | 7.47GB |
| 32 | 1024 | 535 | 28.3 | 7.52GB |
| 32 | 2048 | 673 | 28.0 | 7.75GB（余裕 0.4GB） |
| **33** | **2048** | **659** | **27.6** | **7.28GB（余裕 約 0.9GB）** |
| 34 | 1024 | 501 | 26.8 | 6.59GB |
| 34 | 2048 | 644 | 26.8 | 6.82GB |

**判断**: `-ncmoe 33 -ub 2048` を採用。最速の 32/2048 とは生成速度がほぼ同じで、VRAM の余裕が約 0.9GB 残ります。

**わかったこと**:
- `-ncmoe` を 29 以下にすると VRAM が溢れ、生成が 30 → 19 tok/s に落ちる
- 実サーバーは KV キャッシュの分だけ VRAM を多く使うため、`llama-bench` での境界より 1〜3 層ぶん大きい側に余裕を持たせる必要がある
- `-ub` を 512 → 2048 にすると、プロンプト処理が約 4.7 倍（140 → 659 tok/s）になる。VRAM はその分使う

### 3-3. スレッド数（`-t`）

`llama-bench` で比較しました。

| スレッド数 | 傾向 |
|---|---|
| 8〜16 | 生成はほぼ同じ（約 29〜30 tok/s） |
| 24 | 生成 27 tok/s |
| 32 | 生成 26 tok/s（物理コア数を超えると悪化） |

プロンプト処理は 12 以上で頭打ちになったため、**`-t 12` を採用**。

> 補足: 導入手順書の例は `-t 16` から始める書き方になっています。計測の結果、実際の既定は 12 です。

### 3-4. 全 expert を CPU に移して 128K コンテキストへ（現在の既定）

速度優先の構成では、コンテキストは 16K までしか使えませんでした。
そこで MoE expert を全 40 層とも CPU / RAM に移し、空いた VRAM をコンテキスト長に回しました。

| 構成 | `-ncmoe` | `-c` | pp (tok/s) | tg (tok/s) | VRAM |
|---|---|---|---|---|---|
| 速度優先 | 33 | 16384 | 659 | 27.6 | 7.28GB |
| 全 expert を CPU | 40 | 16384 | 568 | 23.4 | 3.91GB |
| 全 expert を CPU | 40 | 65536 | 564 | 23.4 | 5.06GB |
| **全 expert を CPU（採用）** | **40** | **131072** | **566** | **23.4** | **6.65GB** |

**判断**: 生成速度は約 15% 落ちるが、コンテキストが 8 倍になり VRAM にも余裕がある。長文を扱う用途を優先して既定に採用。

**動作確認**: 約 10 万トークンの文章の中ほどに埋め込んだ合言葉を正しく答えられた（プロンプト処理 124 秒、805 tok/s、生成 22.9 tok/s、VRAM 6.67GB）。

### 3-5. KV キャッシュの量子化（q8_0）

KV キャッシュを f16 から q8_0 に変えると、生成速度はほぼ変わらずに VRAM を削減できました。

| KV | `-c` | tg (tok/s) | VRAM |
|---|---|---|---|
| f16 | 131072 | 23.4 | 6.65GB |
| **q8_0（既定）** | **131072** | **23.0** | **5.43GB** |
| q8_0 | 262144 | 23.0 | 7.50GB |

**判断**: q8_0 を既定にした。128K で VRAM が約 1.2GB 減り、モデル上限の 262K まで使える。

**動作確認（262K）**: 約 20 万トークン（200,566）の前半と後半に埋め込んだ合言葉 2 つを両方正しく答えられた（プロンプト処理 282 秒、710 tok/s、生成 18.8 tok/s、VRAM 7.54GB）。

## 4. 最終的な既定と切り替え

`scripts\start-llm-server.ps1` の既定値:

| 引数 | 既定値 | 意味 |
|---|---|---|
| `-NCpuMoe` | 40 | 全 expert を CPU / RAM に置く |
| `-Ctx` | 131072 | 128K コンテキスト |
| `-KvType` | q8_0 | KV キャッシュの量子化 |
| `-Threads` | 12 | CPU スレッド数 |
| `-UBatch` | 2048 | 物理バッチサイズ |
| `-Port` | 8080 | 待ち受けポート |

用途別の切り替え:

```powershell
# 最大コンテキスト（262K）。VRAM の余裕が少ない（他の GPU アプリとの併用は難しい）
powershell -ExecutionPolicy Bypass -File scripts\start-llm-server.ps1 -Ctx 262144

# 速度優先（短いコンテキスト）
powershell -ExecutionPolicy Bypass -File scripts\start-llm-server.ps1 -NCpuMoe 33 -Ctx 16384 -KvType f16

# ゲームなど他の GPU アプリと併用する（VRAM を空ける）
powershell -ExecutionPolicy Bypass -File scripts\start-llm-server.ps1 -NCpuMoe 34
```

## 5. 未確認・今後の検討事項

- **別モデルとの比較**: 密モデルや他の MoE モデルとの比較は行っていない
- **Q5 以上の量子化**: 品質差の確認は未実施。RAM 余裕はあるため、必要なら試せる
- **Thinking 出力**: Qwen3.6 は既定で思考を出力する（API では `reasoning_content` に分かれる）。思考を止める設定は検証していない
- **Open WebUI**: 任意の Web UI は未導入
- **計測の再現性**: 計測は 1 回の実行に基づく。ドライバやビルドを更新したら再計測が必要
- **llama.cpp のバージョン**: b11675 で確認。フラグの書式はビルドによって変わるため、更新時は `llama-server.exe --help` で確認する
